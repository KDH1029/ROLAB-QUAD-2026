# ROLAB-QUAD-2026 GitHub 협업 규칙 (Git Convention)

본 문서는 4인 규모의 4족보행 로봇 자율주행 팀이 코드 충돌 없이 빠르고 안정적으로 개발하기 위한 공식 형상 관리 규칙입니다.

## 1. 브랜치 전략: GitHub-Flow
본 프로젝트는 단일 메인 브랜치 기반의 민첩한 **GitHub-Flow**를 채택합니다.

- **main**: 실제 로봇 환경에서 정상 동작이 검증된 운영(Production) 코드베이스입니다.
- **기능 브랜치**: 작업 시작 전 항상 `main`에서 파생(Checkout)하여 작업합니다.

### 1.1 브랜치 명명 규칙 (Naming Convention)
물리적 충돌 방지 아키텍처에 따라 접두어를 분리합니다.
- `core/<기능명>`: SLAM, Nav2, 하드웨어 센서 등 로봇 기반 기술 (예: `core/fastlio-mapping`)
- `mission/<미션명>`: 대회 개별 과제 제어 로직 (예: `mission/delivery-task`)
- `fix/<버그명>`: 긴급 버그 수정 (예: `fix/imu-latency`)

## 2. 커밋 메시지 규칙 (Commit Convention)
커밋 메시지는 다음과 같은 접두어를 사용하여 작업의 성격을 명확히 합니다.

- `feat:` 새로운 기능 추가 (예: `feat: A* 경로 계획 알고리즘 추가`)
- `fix:` 버그 수정 (예: `fix: 라이다 점군 좌표 왜곡 현상 수정`)
- `docs:` 문서 수정 및 추가 (예: `docs: 아키텍처 블루프린트 PDF 추가`)
- `refactor:` 코드 구조 개선 (예: `refactor: BT 노드 모듈화`)
- `chore:` 빌드 스크립트, 패키지 의존성 등 설정 변경 (예: `chore: package.xml 의존성 추가`)

## 3. Pull Request (PR) 및 병합(Merge) 규율

### 3.1 표준 개발 프로토콜 (평상시)
- 기능 구현 및 테스트가 완료되면 즉시 GitHub에 PR을 생성합니다.
- `main` 브랜치 병합 전 **최소 1명 이상의 동료 엔지니어에게 코드 리뷰(Code Review) 및 승인(Approve)**을 득해야 합니다.
- 병합이 완료된 기능 브랜치는 즉시 삭제하여 원격 저장소를 청결하게 유지합니다.

### 3.2 필드 긴급 대응 프로토콜 (대회 당일 예외 규정)
- 대회장 현장(Field)에서는 시간적 제약이 극심하므로 파라미터 미세 튜닝 등 긴급 수정에 한해 예외를 허용합니다.
- PR 리뷰 절차를 생략하고 로컬 `main` 브랜치에 직접 병합(Direct Merge) 후 원격 저장소로 `Push`하는 것을 허용합니다.
- 단, 긴급 푸시 전 반드시 동료에게 구두로 작업 내용을 전파해야 합니다.

## 4. 디렉토리 물리적 분리 준수
Git 충돌(Conflict)을 원천 차단하기 위해, 각 개발자는 배정된 도메인 디렉토리에만 접근합니다.

- **엔지니어 A (기반 기술 담당)**: `src/core/` 디렉토리 하위 패키지만 수정
- **엔지니어 B (미션 제어 담당)**: `src/missions/` 디렉토리 하위 패키지만 수정
- 공통 메시지 타입(Msg/Srv/Action) 등 인터페이스 변경이 필요할 경우, 담당자 간 사전 협의 후 한 명의 엔지니어가 전담하여 통합 수정합니다.
