## 왜 뎁스카메라인가 — 라이다와의 역할 분담

기존 XT16 라이다는 16채널이라 수직 해상도가 성겨서, 발 디딜 자리 수준의 정밀한 지형
(구멍, 턱, 계단 단차)을 못 본다 — `gosu_slam`에서 이미 확인된 한계("바닥 링 간격 0.15m ≈
구멍 크기라 구멍이 링 사이로 빠짐", 그래서 팀은 발 힘(`foot_force`) 기반 우회 전략을 택함).

**역할 분담안**:
- **라이다 + FAST-LIO**: 전역 위치추정(SLAM), 방 안에서 "지금 어디 있는지" — 바뀌지 않음
- **뎁스카메라**: 로봇 바로 앞 근거리 지형의 정밀 높이맵(elevation map) — 구멍/계단/턱을
  구분해서 "다음 발을 어디 디딜지" 결정하는 데 씀

이 방향은 `gosu_slam/README.md`의 "다음 대회 — 3D 지형" 섹션에 이미 설계 메모로 있던
`MEVIUS2 Go2 제어 프레임워크`(height_scan, elevation_map, RL 컨트롤러 50Hz)와 같은 계열.

## ★ 카이스트(명현 교수 연구실) 사례 조사 완료 + 범위 확정 (2026-10-03)

유튜브 "더헤럴드" 인터뷰 영상 + 사용자가 정리한 자료로 "DreamStep" 아키텍처 확인:
① SLAM(라이다+비전) ② 위험도 기반 경로계획(Risk-aware Planning) ③ 블라인드 보행
제어기(DreamWalk, RL 학습) ④ GPS-denied 위성지도 매칭.

**범위 결정**: 우리는 ①(라이다+비전 SLAM)은 이미 FAST-LIO로 되어 있고, ③(RL 블라인드
보행)은 GPU 병렬 시뮬레이터+도메인 랜덤화까지 필요한 연구실 단위 프로젝트라 D-32일에
비현실적(스킵), ④(위성지도)는 실내 경기장이라 해당 없음(스킵). **②(위험도 기반
경로계획)만 가져온다** — 기존 `ego_planner`(이분법 장애물 필터)가 못 하는, "최단"이 아니라
"덜 위험한" 경로를 짜는 레이어를 새로 추가.

### 설계
```
위험도 그리드 생성(지형 거칠기+경사) → 위험도 가중 A* → 웨이포인트 ──→ 기존 ego_planner
(뎁스카메라가 근거리 정밀 입력,                                        (웨이포인트 사이
 지금은 라이다 지도로 프로토타입)                                       지역회피는 안 바꿈)
```

### 프로토타입 검증 완료 — `src/risk_grid_prototype.py`
어제 만든 `arena0921_map`으로 바로 돌려봄. 15cm 그리드, 셀별 지면높이(10퍼센타일)로
elevation map을 만들고, 이웃 셀과의 기울기 + 셀 내부 높이 분산(거칠기)으로 위험도(0~100)
합성. 결과:
- **높이 임계값을 하나도 안 줬는데, 어제 수동으로 찾은 계단 쐐기 구조(X:0.5~1.5,
  Y:2.5~4)가 자동으로 고위험(짙은 빨강)으로 나왔다** — 순수 기하학적 특징만으로 식별됨.
  어제 방식(높이 임계값 수동 보정)보다 더 일반적이고 강건한 방법으로 보임.
- A*로 시작(0,0)→목표(1.5,5.5) 경로를 위험도 고려/무시 두 버전으로 비교 — **위험도
  고려 경로가 쐐기 구조를 피해서 살짝 돌아가는 것 확인됨**(Y:2~4 구간에서 두 경로가
  갈라짐). 개념 검증(PoC) 성공.

## ★ 카메라 확정 + 드라이버 설치 완료 (2026-10-03)

**기종**: Intel RealSense **D435i** (IMU 내장형, 기존 보유 장비)

**설치**: `sudo apt install ros-jazzy-realsense2-camera` (librealsense2 SDK 자동 포함).
노트북(victus)에 USB-C로 직결, nuc16은 누리관에 있어서 지금은 노트북에서 개발/테스트 중
— 나중에 로봇 마운트 시 nuc16으로 옮길 것.

**겪은 문제 — IMU 켜면 USB 불안정**: 처음엔 기본 설정(depth+컬러만)으로 완벽히 떴는데,
`enable_gyro:=true enable_accel:=true`로 IMU까지 켜니 **2초 간격으로 USB가 끊겼다 붙었다
반복**(`dmesg`로 확인, `VIDIOC_QBUF ... No such device` 에러 폭주, 로그 파일이 수백MB로
불어남). USB-C 연결에서 depth+컬러+IMU 동시 사용이 대역폭/전력 한계를 넘는 것으로 추정.

**해법(임시)**: **IMU는 끄고 depth+컬러만 사용**. 기본 `rs_launch.py`(인자 없이) 실행하면
26~29Hz로 안정적, 에러 0건. 로봇 자체 IMU(`/lowstate`, 500Hz)가 이미 있어서 당장 급하지
않음 — 나중에 USB-A 연결이나 별도 전원 공급으로 바꾸면 재시도 가능.

```bash
source /opt/ros/jazzy/setup.bash
ros2 launch realsense2_camera rs_launch.py
# 토픽: /camera/camera/depth/image_rect_raw, /camera/camera/color/image_raw 등
```

**함정 기록**: `pkill -f`로 반복 강제종료하며 테스트하다 보니 디버그 로그가 초당 수만 줄씩
쌓여 `/tmp`에 250MB+ 파일이 여러 개 생겼었음 — 반복 재시도할 땐 로그 크기 주기적으로 확인할 것.

## ★ depth → 포인트클라우드 변환 검증 완료 (2026-10-03)

실제 D435i 프레임 1장을 받아서 intrinsics(fx=fy=431.08, cx=422.28, cy=240.89, 왜곡 없음
— 이미 보정된 rectified 스트림)로 핀홀 투영해 3D 포인트클라우드 변환 확인.

```
결과   265,096점 (848x480 중 65.1% 유효, 범위 0.17~3.98m)
밀도   약 22,500 pts/m^2 — 라이다 전체평균(약 1,143 pts/m^2) 대비 약 20배
```

**결론: 구멍/계단 단차 탐지에 필요한 밀도는 확실히 충분하다.** 코드는
`src/depth_to_pointcloud.py`(프레임→포인트클라우드), `src/verify_depth_density.py`(밀도 비교).

**주의**: 이번 변환은 카메라 광학 프레임 기준(바닥 보정 안 됨, 핸드헬드로 아무 데나 비춘
테스트). 실제로 위험도 그리드에 쓰려면 로봇 마운트 후 **카메라 장착 각도/높이로 외부파라미터
보정**(camera → base_link 변환)이 필요 — 아직 안 함, 로봇 마운트 전까지는 불가능.
